# 任务模板指南

本文以 `plugin_manager/plugins/task/` 为边界，说明当前实际支持的模板格式与新增方法。模板是任务数据规范，不是 Skill，也不是 DAG 配置。

## 1. 模板放在哪里

```text
templates/
├── basic/                  # 默认通用模板
│   ├── template.yaml
│   └── schema.json
├── structured/             # 通用结构化模板
│   ├── template.yaml
│   └── schema.json
└── finance_evaluation/     # 按需新增的类别模板
    ├── template.yaml       # 必需：默认数据
    ├── schema.json         # 必需：字段校验规则
    └── intent.json         # 可选：意图匹配规则
```

目录名是内部模板 ID：1～64 个英文字母、数字、下划线或连字符。Harness 不需要知道这个 ID。没有 `intent.json` 的模板可以直接通过 TaskManager 使用，但不参与插件的关键词路由。

配置位于 `config/task.json`：

```json
{
  "templates_dir": "../templates",
  "fallback_template": "basic"
}
```

这是两个配置字段的摘录，修改时保留其他现有字段。`templates_dir` 相对总配置目录；`fallback_template` 指定未匹配或匹配有歧义时使用的兜底模板，不是固定选择的业务模板。

## 2. 新增模板：三个文件

以下金融例子仅演示文件格式，不代表公司真实业务规范。将字段和约束替换成经确认的业务要求。

### template.yaml：只写已确定的默认值

在 `templates/finance_evaluation/template.yaml` 写：

```yaml
domain: finance
output:
  format: jsonl
```

不要给需要向用户确认的题量、题型、数据来源编造默认值。默认值会与输入递归合并：对象合并、数组替换、用户显式传入的 null 保留并接受校验。仅在 Schema 的 `default` 中填写值不会自动补值，真正的默认值应放在本文件。

### schema.json：声明完整任务需要什么

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "objective": {"type": "string", "minLength": 1},
    "domain": {"const": "finance"},
    "dataset": {"type": "string", "minLength": 1},
    "question_count": {"type": "integer", "minimum": 1},
    "question_types": {
      "type": "array",
      "items": {"type": "string", "enum": ["single_choice", "case_analysis"]},
      "minItems": 1,
      "uniqueItems": true
    },
    "output": {
      "type": "object",
      "properties": {"format": {"enum": ["jsonl", "json"]}},
      "required": ["format"],
      "additionalProperties": false
    }
  },
  "required": ["objective", "domain", "dataset", "question_count", "question_types", "output"],
  "additionalProperties": false
}
```

规则：

- 使用 JSON Schema Draft 2020-12，根类型必须是 `object`。
- `required` 控制必填字段；`properties` 仅声明字段，并不意味着必填。
- `additionalProperties: false` 拒绝未声明字段；只有确实需要扩展时才放开。
- 默认数据可以是不完整的，但合并用户数据后必须通过校验。
- 支持本地 `$ref`，例如 `#/$defs/xxx`；不支持外部 URL 或其他文件的引用，不联网获取 Schema。
- Schema 不会检查数据集文件是否存在、题目是否正确、闸门是否实际通过。这些属于执行工具和节点验证。

建议声明 `objective`，让业务任务能直接形成规划描述。否则规划时需要 Harness 另外传顶层 `task`。

### intent.json：让插件识别这个类别

```json
{
  "keywords": ["金融评测", "金融题包", "finance evaluation"],
  "priority": 10
}
```

只支持 `keywords` 和 `priority`：关键词列表必填、不能包含空白词；优先级可省略，默认为整数 0。不要把字段标题、描述或 Schema 写入这个文件。

新增其他类别时，复制目录结构，独立编写各自三个文件。不要直接复制金融关键词到法律模板。

## 3. 插件怎么选模板

插件从以下字符串拼接匹配内容：

- 顶层 `task`。
- `task_data.objective`。
- `task_data.domain`。
- `task_data.category`。

不会遍历任意业务字段或输入文件路径，也不会调用 LLM 做类别识别。

匹配是忽略大小写的子串规则；命中任一关键词即可成为候选，按下列顺序比较：

1. `priority` 越大越优先。
2. 优先级相同时，不同命中关键词越多越优先。
3. 再相同时，命中关键词总字符数越多越优先。
4. 最终仍并列，或没有候选，使用兜底模板。

关键词写准确，避免使用过宽的“评测”“生成”等词把所有任务吸入同一类别。该匹配不会理解否定句或隐含意图；例如“不要做金融评测”仍会命中“金融评测”。对语义要求高时需另行开发识别策略。

模板或 `intent.json` 格式错误会明确报错，不当作未命中静默忽略。当前内置模板未配置业务关键词，因此未新增业务模板时默认使用 `basic`。

## 4. Harness 怎么调用

Harness 不传 `template_id`。Task 和 Graph 是同级独立子插件，由 Harness 决定调用顺序：

```python
from plugin_manager import PluginManager

async with PluginManager() as manager:
    await manager.start("task")
    checked = await manager.call("task", "check", {
        "task": "生成金融评测题包",
        "task_data": {"objective": "生成金融评测题包"}
    })
    if checked["status"] == "ready":
        await manager.start("graph")
        result = await manager.call("graph", "prepare", checked["request"])
    else:
        issues = checked["issues"]  # Harness 汇总所有问题后组织一轮提问
```

Task 不导入或调用 Graph，也不连接工具、模型或数据库。Graph 不再执行模板检查。直接调用 Graph 代表调用方自行承担任务完整性检查。

使用上述示例模板时，缺少 `dataset`、`question_count`、`question_types`，返回：

```json
{
  "status": "needs_input",
  "issues": [
    {"path": "/dataset", "message": "Required field is missing", "code": "required"},
    {"path": "/question_count", "message": "Required field is missing", "code": "required"},
    {"path": "/question_types", "message": "Required field is missing", "code": "required"}
  ]
}
```

Harness 根据全部问题组织一轮自然语言询问，不必逐字段提问。用户回答由 Harness 转成结构化字段，并重传累计完整任务：

```python
checked = await manager.call("task", "check", {
    "task": "生成金融评测题包",
    "task_data": {
        "objective": "生成金融评测题包",
        "dataset": "datasets/finance.jsonl",
        "question_count": 100,
        "question_types": ["single_choice", "case_analysis"]
    }
})
```

成功返回 `status: ready`、`intent`（模板选择原因及关键词）、`task_definition`（ID、模板哈希、默认值合并后的数据）与 `request`。将 `request` 传给 Graph 的 `prepare`、`run` 或 `plan`。

- `check` 可指定 `target_operation` 为 `prepare`（默认）、`run` 或 `plan`；该字段不会转发到 Graph。显式目标通常无需规划描述，`plan` 则始终需要描述。
- `task_data` 是结构化任务数据，无需先生成 YAML 文件。自然语言模式将校验后的数据放入 `request.context.task_data`；不会自动映射成节点输入。
- 只传 `task` 时，若模板声明 `objective`，可将描述用于该字段；显式传入 `task_data` 则应提供必填字段。
- 基本模板下，只有显式 `goal` 时可派生 `objective`；自定义模板不会编造业务字段。
- 自定义模板不含 `objective` 时，规划需要单独提供顶层 `task`。
- Task 不保存多轮草稿，Harness 每次重新提交累计完整数据。
- 其他操作：`templates.list` 无参数，`templates.get` 接收 `template_id`，`parse_yaml` 接收 `text`。原生 `TaskManager` 仍提供创建、校验、保存等函数。
- Task 同时检查请求信封的字段类型：`goal`、`initial_conditions`、`inputs`、`context` 等；规划请求不能携带仅供显式编译的 `proposal`、`order_hints`，此类冲突返回 `needs_input`，不会静默丢弃。
- 任务校验通过不代表业务工具可执行、题目正确或业务闸门已通过；事实语法、技能引用和图语义仍由 Graph 验证。

## 5. 新增后怎么验证

在插件所在项目中直接使用内部 TaskManager 检查，不需要连接模型或工具：

```python
from plugin_manager.plugins.task import TaskManager

manager = TaskManager()
assert "finance_evaluation" in manager.list_templates()

selection = manager.recognize("生成金融评测题包")
assert selection.template_id == "finance_evaluation"

validation = manager.validate(
    {"objective": "生成金融评测题包"},
    template_id=selection.template_id,
)
assert not validation.valid
print(validation.issues)

task = manager.create({
    "objective": "生成金融评测题包",
    "dataset": "datasets/finance.jsonl",
    "question_count": 100,
    "question_types": ["single_choice"]
}, template_id=selection.template_id)
assert task.data["output"]["format"] == "jsonl"
```

这里是开发者内部验证，所以会访问模板 ID；Harness 正常调用无需使用。

至少检查：类别命中、无匹配回退、同分歧义、必填缺失、字段类型错误、默认值合并、业务样本能通过校验。模板每次操作重新读取，不需要重启 Python；已开始的任务不会因此自动重新检查或重编译。

新增模板不需要修改 Python 代码或中央模板清单。只要放入配置的模板根目录，文件格式正确，即会被发现。

## 需求澄清与规格确认

`check` 仍是离线模板与请求结构检查，`ready` 不表示已经过语义澄清或用户确认。新增操作不调用 Graph，也不执行工具：

| 操作 | 请求 | 返回 |
|---|---|---|
| `analyze` | 与 `check` 相同的任务请求，不含 `target_operation` | `needs_clarification` 或 `awaiting_confirmation`，以及 `draft` |
| `revise` | `draft`、可选 `answers`、可选 `changes` | 新版本草稿，原草稿不变，确认状态清除 |
| `confirm` | `draft`、`version`、`revision`、`approved: true` | `confirmed`、`confirmed_spec` 和可提交 Graph 的 `request` |

典型调用（Manager 已注册 `task`）：

```python
await manager.start("task")
result = await manager.call("task", "analyze", {"task": "用户描述"}, timeout=90)

# Harness 保存 draft，组织问题和事实核查，收集实际回答。
result = await manager.call("task", "revise", {
    "draft": result["draft"],
    "answers": {"返回的问题ID": "用户实际回答"},
}, timeout=90)

# 仅当 awaiting_confirmation：向用户展示 summary、决策记录和建议。
# 用户明确批准后，回传他看到的准确版本及 revision。
draft = result["draft"]
confirmed = await manager.call("task", "confirm", {
    "draft": draft,
    "version": draft["version"],
    "revision": draft["revision"],
    "approved": True,
})
await manager.start("graph")
prepared = await manager.call("graph", "prepare", confirmed["request"], timeout=90)
```

这些代码段对应不同的交互轮次，不能不看状态直接连续执行。没有未决问题、冲突、假设且模板与阻塞规则检查均满足后，才会进入 `awaiting_confirmation`；规格字段还要求目标、范围、输出和验收标准完整。模型的检查结论不是事实真伪的证明。

`questions` 是当前可回答的用户决策，`fact_requests` 是应由 Harness 查证的事实；默认每轮合计最多 3 个。不展示依赖未解决的问题。用户也可以在一次回答中同时明确前提与后续决定；未提供前提时单独回答下游问题会拒绝。未答问题会保留，模型不能自行删除。已答问题不能再次提问，但调用方可以按旧 ID 显式更正回答，历史记录保留。

`changes` 修改原始请求字段；其中 `task_data` 按顶层字段合并。原始输入在 `base_request`，模型提取的候选字段在 `review.task_data`，用户回答/宿主提供的事实在 `answers` 和 `decision_log`。系统建议和假设分别存放，不自动变成用户决定。`decision_log` 保留问题、推荐、选项和回答；`changes_log` 记录请求修改。最终规格从这些记录生成，仍需用户审阅是否忠实表达了决定。

## Task 自己的模型配置

修改 `task/config/task.json` 中的 `llm`，其他模板配置保持不变：

```json
{
  "base_url": "http://模型地址:8000/v1",
  "model": "实际模型名称",
  "api_key_env": "TASK_LLM_API_KEY",
  "timeout": 60.0
}
```

`base_url` 是 API 根地址，客户端追加 `/chat/completions`。密钥通过环境变量提供；不需要认证时省略 `api_key_env`。默认 `llm: null`：`check` 仍可用，`analyze/revise` 明确抛出 `TaskProviderUnavailable`，不伪造语义分析。Task 的模型与 Graph/Meta 模型配置分开，Harness 无需注入。外层 `timeout` 限制整次澄清，包括最多两次模板路由复核；Manager 调用超时也需设置足够长。

配置 `rules.general` 声明通用清单，`rules.templates.<模板ID>` 声明领域清单。每条规则包含唯一 `id`、`text`、`blocking`。模型必须逐条给出依据；阻塞项未满足时不能确认。提取信息导致模板类别变化，会用新模板和规则重新分析一次；反复变化则报错，要求明确领域。原有模板 Schema 继续进行确定性校验，不被模型清单替代。

## 版本与边界

- `revise` 增加版本并关联上一 `revision`，不会原地修改旧确认。模板内容或当前实例的检查清单变化后，需要重新分析再确认。
- 调用方必须保存最新草稿、向用户展示版本，再把明确批准传给 `confirm`。模型输出协议不包含批准字段。
- `revision` 是内容摘要，用于发现内容改动，不是签名或身份认证。Task 无状态，无法知道调用方是否重放了另一个旧快照；最新版本、用户身份与批准事件由 Harness 管理。
- 确认规格和决策记录随通用 `context.task_spec` 进入 Graph；Graph 将上下文保存在图元数据中。Graph 不依赖 Task，也不强制所有调用先经过 Task。
- 模型的含义理解、规格是否忠实于自然语言回答、材料真实性仍需实际模型与业务验证；通过结构测试不等于语义正确。

参考机制：[OpenSpec 的行为规格](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)、[grilling 的依赖分轮访谈](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)、[老刀关于决策纪要和分层清单的实践](https://laodao-ai.com/posts/spec-still-off-track/)。这里借鉴机制，不依赖其 CLI 或特定 Harness。
